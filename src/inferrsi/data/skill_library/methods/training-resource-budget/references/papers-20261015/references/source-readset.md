## ZO: ZeRO-Offload

- Full title: ZeRO-Offload: Democratizing Billion-Scale Model Training. Jie Ren, Samyam Rajbhandari, Reza Yazdani Aminabadi, Olatunji Ruwase, Shuangyan Yang, Minjia Zhang, Dong Li, Yuxiong He.
- [Original metadata](https://arxiv.org/abs/2101.06840), [pinned v1 PDF](https://arxiv.org/pdf/2101.06840v1). Only v1 listed: 2021-01-18 02:11:25 UTC. 14 PDF pages.
- Actual relevant readset: §§2–3.5, including §3 footnotes 1–2 and Fig. 2/Table 1; §§4.1–4.2/Figs. 3–4 and associated schedule discussion; §§5.1–5.2 including displayed CPU-Adam algorithm and Fig. 6; §§6.1–6.2.4, Tables 2–4, Figs. 7–13 and associated prose. Visually checked PDF pp. 5 and 11, especially Table 1, Table 4 and Figs. 11–13. Figure 5's code screenshot was not independently transcribed or implementation-audited.
- SHA256 of downloaded pinned PDF: 361dd58aadd744a79b17268b985034de00b9cf7423c000f9aa1549bfa382146c.

F, setup: GPT-2-like Transformer models; mixed FP16/FP32 Adam. Single-node capacity/throughput tests use DGX-2 with 16 V100 32-GB GPUs, two Xeon Platinum 8168 CPUs, 1.5-TB DDR4, reported bidirectional PCIe 32 GB/s. Scaling uses eight DGX-2 nodes and an InfiniBand switch. Table 3 changes depth, width, microbatch and model parallelism by model size. Fig. 8 uses total batch 512, matched microbatches and gradient accumulation, with delayed parameter update (DPU) disabled. Fig. 10 uses total batch 512 but the largest feasible microbatch for each system. These are different comparison controls.

F, evidence ledger:
- §§3.1–3.5: graph cuts minimize host/device bytes after fixing O(MB) forward/backward compute and FP16 weights on GPU; O(M) optimizer operations and FP32 master weights/moments move to CPU, as do FP16 gradients. The stated minimum is 4M bytes per iteration for whole model-state offloads in this model. The analysis excludes activation offload and residual-state costs; it is not an arbitrary-hardware global optimum.
- Table 1 prints the final row as 4M device memory and 8× reduction versus 16M. These entries are mutually inconsistent; the surrounding placement prose leaves FP16 parameters plus transient gradient buffers on GPU. Do not silently replace the printed number or treat the table as a reliable total-peak formula.
- §4.2: reduce-scatter gradients before offloading each owned partition; parallel CPU updates; return updated parameter partitions and allgather. Partitioning prevents duplicated host updates/traffic across data-parallel replicas. Claims about increasing CPU resources apply across compute nodes, not indefinitely across more GPUs sharing a fixed host.
- §5.1/Table 4: CPU-Adam versus PyTorch CPU Adam latency in seconds for 1B/2B/4B/8B/10B parameters: 0.22/0.51/1.03/2.41/2.57 versus 1.39/2.75/5.71/11.93/14.76. PyTorch GPU (L2L) comparator: 0.10/0.26/0.64/0.87/1.00. SIMD/loop-unrolling/OpenMP and tiled copy are combined; isolated attribution for each is unreported.
- §6.2.1/Fig. 7: 13B fits one V100 versus 1.4B PyTorch; L2L fits 17B. Capacity leadership therefore does not imply throughput leadership. §6.2.2/Fig. 8: ZeRO-Offload is 14% faster on average, up to 22%, than L2L in reported TFLOP/s under the matched batch comparison. The paper models L2L traffic as 28M versus 4M bytes; this is historical baseline accounting.
- §6.2.2/Fig. 10: up to 70B on 16 GPUs with model parallelism, over 30 TFLOP/s/GPU; not a same-size speed ratio against a baseline that OOMs. §6.2.3/Fig. 11: 10B model aggregate throughput approximately scales through 128 GPUs, but ZeRO-2 becomes faster at 64/128 GPUs once both can use similar microbatches and offload retains a transfer cost. Do not label this fixed-total-work strong scaling without the missing batch/scaling controls.
- §5.2/§6.2.4/Figs. 9,12,13: one-step DPU intentionally uses stale updates after an initial ordinary-training period. At microbatch 8, throughput ratio with/without DPU is reported 1.12–1.59×. Convergence examples enable DPU after 40 iterations: GPT-2 pretraining for 100K iterations shows initially slower loss then catching up; BERT-large SQuAD fine-tuning reaches F1 92.8 in both variants. These two workloads do not establish universal convergence safety.

## CM: Checkmate

- Full title: Checkmate: Breaking the Memory Wall with Optimal Tensor Rematerialization. Paras Jain, Ajay Jain, Aniruddha Nrusimha, Amir Gholami, Pieter Abbeel, Kurt Keutzer, Ion Stoica, Joseph E. Gonzalez.
- [Original metadata](https://arxiv.org/abs/1910.02653), [pinned v3 PDF](https://arxiv.org/pdf/1910.02653v3). v1 2019-10-07; v2 2020-03-12; read v3 2020-05-14 17:46:43 UTC. 15 PDF pages. No revision mixing.
- Actual relevant readset: §§4.1–4.10, Eqs. 1–9, Theorem 4.1 and Lemmas 4.1–4.2; §§5.1–5.3 and Algorithms 1–2; §§6.1–6.5, Eq. 10, Tables 1–2, Figs. 5–6; Appendices A–D, Figs. 7–8. Visually checked PDF pp. 9–10 for Figs. 5–6/Table 2. PDF p. 2 contains a figure with embedded manuscript text; its obsolete equation/section snippets were not used in place of the body formulation.
- SHA256: 8355cc2ecac072863fde2542585f8da0be30924e6181d9b05a36a63b22a1f694.

F, model and evidence:
- §§4.1–4.10: static DAG; each value has memory Mv and per-evaluation cost Cv. Binary R[t,i] selects evaluation, S[t,i] retention. U[t,k] accounts for memory just after an output exists and before dependencies are freed. Inputs/parameters and parameter-gradient reserve remain resident (Eq. 2). FREE variables require no later user and no retained checkpoint. Objective minimizes summed evaluation costs under per-event memory budget, not transfer time.
- §4.6/Eq. 8 restricts to a supplied topological order and frontier-advancing stages. This narrows the feasible set; optimality is within this formulation, not all possible reordered/parallel executions. Example: an eight-layer linear graph with unit costs and memory budget 4 solves in 0.23 seconds versus 9.4 hours unpartitioned, to the same objective. Appendix A's corresponding integrality-gap example is 1.18 versus 21.56. These are optimization examples, not training throughput.
- §4.10: additive timings from layer profiling on target hardware, shapes and batch; dense tensors use four-byte floats in the evaluated model. §6 implementation is TensorFlow 2.0/Keras/Gurobi. Most ordinary solves use 3600-second limit on at least 24 CPU cores. §5 reports no feasible solution for a DenseNet161 instance within one day; solver timeouts do not prove infeasibility.
- §6.3/Fig. 5: overhead is profile-model time relative to no-rematerialization ideal, using one NVIDIA V100. U-Net batch 32, 416×608 images, 16-GB budget: reported 1.20× speedup over linearized greedy and 1.38× over linearized sqrt(n). This is not directly measured whole-training speedup. VGG16 batch 256 and MobileNet batch 512 use 224×224.
- §6.4/Eq. 10/Fig. 6: maximize feasible batch subject to 16 GB and at most one extra forward pass in statically computed FLOPs. The nonlinear formulation gets a one-day limit; returned batch is a lower bound if optimality is unproved. MobileNet 224×224: 1105 versus 215 checkpoint-all and 640 linearized-greedy; author reports 5.1× and 1.73× respectively. U-Net 416×608: 61 versus 16 checkpoint-all and 35 best plotted heuristic. These are theoretical feasible-batch results, not observed time-to-quality or a guarantee that enlarged batch preserves training behavior.
- §§5.1–5.3/Algorithm 2: round S, then restore minimal necessary R to satisfy computation dependencies. Capacity is not guaranteed by this procedure. The authors empirically use 10% memory allowance; Appendix D says that allowance is overly conservative for MobileNet.
- §6.5/Table 2: two-phase approximation COSTapprox/COSTopt, geometric mean across mutually feasible budgets, in FLOPs: MobileNet 1.06, VGG16 1.01, VGG19 1.00, U-Net 1.03, ResNet50 1.05. It is neither a worst-case 1.06 approximation guarantee nor a whole-job speed ratio. Appendix D/Fig. 8 compares randomized versus deterministic two-phase rounding with profile-cost milliseconds.

## OL: OLLA

- Full title: OLLA: Optimizing the Lifetime and Location of Arrays to Reduce the Memory Usage of Neural Networks. Benoit Steiner, Mostafa Elhoushi, Jacob Kahn, James Hegarty.
- [Original metadata](https://arxiv.org/abs/2210.12924), [pinned v2 PDF](https://arxiv.org/pdf/2210.12924v2). v1 2022-10-24; read v2 2022-11-02 19:22:24 UTC. 14 PDF pages.
- Actual relevant readset: §§2.1–2.3/Figs. 3–4; §§3.1–3.5, Eqs. 1–9/Function 1; §§4.1–4.5, Eqs. 10–15/Functions 2–5/Figs. 5–6; §§5.1–5.7/Figs. 7–14; §6's placement/lifetime comparison. Visually checked PDF p. 10 (Figs. 11–14 and §5.7). Individual bar values were not digitized.
- SHA256: 69aebb2c874871e363ccec93e2ea15891e91c793153cde37004d17ea12ddef0b.

F, model and evidence:
- §3: DAG tensors are edges (possibly multiple consumers), with known sizes. Binary creation C[e,t] and preservation P[e,t] enforce exactly one creation, availability of all inputs, contiguous retention and simultaneous sibling outputs. Integer A[e] is a base address in one preallocated buffer, not GPU/CPU/SSD tier placement. Concurrent live tensors cannot overlap addresses. Objective minimizes maximum A[e]+size[e]. It neither offloads nor recomputes tensors.
- §§4.1–4.5: bound variable ranges using earliest/latest schedules and useful lifetimes; drop pairwise constraints for proven nonoverlapping tensors; add control edges to force safe early weight updates; split lifetime optimization (Eq. 14) from address optimization (Eq. 15); preplace nested activation lifetimes. The split relies on their empirical ability to remove fragmentation, not a universal proof that independently optimized lifetimes always admit ideal packing.
- §§5.1–5.2: PyTorch 1.11, torchtext/torchvision 0.12, torch.FX and Gurobi 9.1.1; Xeon Gold 6138 at 2.0 GHz plus A100 40 GB. Eleven families: AlexNet, EfficientNet, GoogleNet, MNASNet, MobileNet, ResNet, ResNet3D, Transformer, VGG, ViT, XLM-R, at batches 1/32. Graph size ranges from AlexNet 118 to XLM-R 2007 operators.
- §5.3/Fig. 7: node-reordering comparison excludes fragmentation, measuring peak requested operator memory/resident demand rather than allocator-reserved bytes. Maximum reduction 38%; mean 22.5% at batch 1, 10.1% at batch 32. Less leverage at large batch is attributed to forward activations dominating gradients.
- §5.4/Fig. 8: fragmentation defined (MR−RS)/MR at peak reserved memory MR. PyTorch mean fragmentation 7.9% at batch 1, 26.1% at batch 32; OLLA fully removes it in evaluated scenarios. Do not add these percentages to lifetime percentages: denominators differ.
- §§5.5–5.6/Figs. 9–12: median ordering solve 1.4±0.2 s, address generation 5.7±0.6 s; difficult EfficientNet ordering takes 2 min for batch-1 optimum, 5 min to within 1% at batch 32. GoogleNet/EfficientNet packing reaches <1% fragmentation within 5 min. The text's uncertainty notation is retained; no unreported confidence interpretation is added.
- §5.7/Fig. 13: cap each of the two optimizations at five minutes; overall memory reduction averages 30.4% at batch 1 and 36.1% at batch 32 versus PyTorch. §5.7/Fig. 14 estimates about five minutes runtime saved over one million batch-32 iterations by comparing allocator costs with upfront optimization. Total training time under the two schemes was explicitly not directly measured; batch-1 runtime estimate is unreported.
- Isolated ablations of every pruning/early-update/preplacement optimization and distributed-training interactions are unreported. No conclusion about current PyTorch allocator behavior follows from the 1.11 comparison.

## AL: Alpa

- Full title: Alpa: Automating Inter- and Intra-Operator Parallelism for Distributed Deep Learning. Lianmin Zheng, Zhuohan Li, Hao Zhang, Yonghao Zhuang, Zhifeng Chen, Yanping Huang, Yida Wang, Yuanzhong Xu, Danyang Zhuo, Eric P. Xing, Joseph E. Gonzalez, Ion Stoica.
- [Original metadata](https://arxiv.org/abs/2201.12023), [pinned v3 PDF](https://arxiv.org/pdf/2201.12023v3). v1 2022-01-28; v2 2022-06-03; read v3 2022-06-28 19:36:44 UTC. 20 PDF pages. A v1 PDF was fetched before metadata resolution but not used as evidence.
- Actual relevant readset: §§2–8.6 including every method, limitation and evaluation subsection; Eqs. 1–6, Algorithm 1, Tables 1–5, Figs. 1–12 and associated prose; Appendix A/Theorem 1/Eq. 7, Appendix B/Tables 6–8, Appendix C/Fig. 13. Visually checked PDF p. 13/Table 5/Figs. 10–11.
- SHA256: cd1dea70769571a5e9298ba0610e04cc514a06ab12018dd7f19a457fd00cd474.

F, model and evidence:
- §4/Eq. 1: choose one sharding algorithm per operator on a homogeneous 2-D logical device mesh, accounting for operator communication and edge resharding. The evaluated ILP estimates bytes/bandwidth and sets compute costs dv to zero, assuming equal arithmetic work among heavy-op shardings and negligible lightweight work. It does not show all equal-FLOP kernels run equally fast. Post-ILP reduce-scatter/allgather can reduce replicated optimizer work without changing total collective bytes.
- §5/Eqs. 2–5: stages are contiguous in a given operator ordering; corresponding forward/backward ops colocate. Objective sum(stage latency)+(B−1)×max(stage latency) for the chosen static GPipe/1F1B timing model. DP chooses stage boundaries and restricted physical submesh shapes; intra-op choices are evaluated per stage/mesh. 1F1B feasibility uses memstage+s×memact≤memdevice. Infeasible stage/mesh pairs get infinite cost. Shape restriction ensures device coverage, not global-optimal search over arbitrary partitions.
- §5.2 says compile/profile stage plans including fusion and memory planning; §8.4 describes accelerating profiling with a piecewise-linear XLA-operation cost model. Do not present all plan costs as directly timed full stages. Search also clusters operators and prunes DP choices.
- §6/Fig. 6: cross-mesh resharding sends each needed tile across slow links then locally allgathers replicated destinations, avoiding redundant slow transfers. Static per-mesh instruction lists avoid continuous driver coordination. Optimal cross-mesh resharding is left to future work.
- §7: no inter-stage communication cost in the plan objective; microbatch count is an external hyperparameter, not internally optimized; static shapes/graphs and linear schedules; no optimization of computation/communication overlap. Two-level solution is not guaranteed globally optimal.
- §8: eight AWS p3.16xlarge nodes, eight V100 16-GB GPUs/node, intra-node NVLink, 25-Gbps cross-node bandwidth; 64 vCPU and 488-GB host memory/node. Metric is aggregate PFLOP/s on warmed-up dummy-data batches; model size grows with GPU count (weak scaling). Global batches: GPT and MoE 1024/FP16; Wide-ResNet 1536/FP32. GPT/MoE sequence 1024; image input 224×224×3. Microbatch tuned per configuration.
- §8.1/Fig. 7: GPT roughly matches grid-searched Megatron-LM v2; MoE beats DeepSpeed 3.5× on 16 GPUs (10B model) and 9.7× on 32 GPUs (27B), where the historical DeepSpeed baseline has no inter-op pipeline and slow network communication dominates. Wide-ResNet achieves author-reported 80% linear-scaling efficiency on 32 GPUs. These are not time-to-quality or equal-model strong-scaling results.
- §8.2/Fig. 8: isolate intra-op search on one eight-GPU node, disabling pipeline and gradient accumulation, with altered model shapes/batches versus §8.1. ILP is compared with data parallel, ZeRO-2/3 and largest-axis sharding heuristic. It cannot be merged numerically with the end-to-end setup.
- §8.3/Fig. 9: at 32 GPUs, Wide-ResNet DP plan is 2.6×/1.6× faster in PFLOP/s than equal-operator/equal-layer restrictions; equal-layer equals DP on homogeneous GPT. §8.5/Fig. 11: local-allgather resharding gives 2.0× throughput over send/recv-only on 32-GPU Wide-ResNet. One-byte signal control is a synthetic upper bound, not executable model semantics.
- §8.4/Table 5: GPT-39B/64-GPU compilation 1582.66 s, profiling 804.48 s, stage DP 1.65 s, other 4.47 s, total 2393.26 s versus >40 h without optimizations. This is one supplied microbatch-count run, not cost of searching all B.
- §8.6/Fig. 12: Wide-ResNet/16 GPUs chooses three stages on 4/4/8 GPUs, with early activation-heavy layers preferring batch partitioning and later weight-heavy work different sharding. Table 4 rounds the 32-GPU Wide-ResNet model to 6.7B while Table 8 says 6.8B; do not silently reconcile.

## ZB: Zero Bubble Pipeline Parallelism

- Full title: Zero Bubble Pipeline Parallelism. Penghui Qi, Xinyi Wan, Guangxing Huang, Min Lin.
- [Original version record](https://arxiv.org/abs/2401.10241v1), [pinned v1 PDF](https://arxiv.org/pdf/2401.10241v1), [same-version HTML](https://arxiv.org/html/2401.10241v1). The original record and PDF both give v1 as 2023-11-30 10:40:34 UTC despite the 2401 identifier; retain that source metadata. 19 PDF pages. arXiv's link boilerplate says "and 2 other authors" while its author list and PDF contain four; use the actual list.
- Actual relevant readset: §§1–7 (all subsections), Tables 1–8/Figs. 1–9; Appendices A–H including Figs. 10–11, Appendix B Eqs. 1–2, Appendix C Algorithm 1 (AdamW rollback), Appendix G Eqs. 3–7, Tables 9–12. Visually checked PDF pp. 7, 11 and 18 for Tables 4,6–8,11 and associated plots/text. The v1 HTML served as an additional same-version methods check.
- SHA256: 0de7cd6efd52eaa3f216129cd186ab755b1045bca1f6ddc422216295a7e9fee9.

F, model and evidence:
- §§1–2: split backward into B (input gradient, critical across stages) and W (parameter gradient, movable after B). Delaying W retains its needed activations/gradients. Table 2's ideal comparison: 1F1B bubble (p−1)(TF+TB+TW), ZB-H1 (p−1)(TF+TB−TW), both peak activations pMB; ZB-H2 bubble (p−1)(TF+TB−2TW), peak (2p−1)MB. Zero-bubble equality depends on timing assumptions and removing the optimizer barrier; it is not a universal empirical zero-idle guarantee.
- §3/Appendix G: schedule ordering/end times with inter-stage F/B dependencies, device sequencing and cumulative activation-memory limits; input p,m, memory cap, profiled TF/TB/TW/Tcomm. Heuristic schedules W into gaps or when memory needs release; ILP is feasible only at limited problem scale. Appendix A proposes parameter-grouped tail W work for overlapping data-parallel allreduce; an isolated measured ablation of that proposal is unreported.
- §4/Appendix C: partial reductions followed by post-update validation; invalid speculative updates roll back and redo using global clipping/NaN state. AdamW arithmetic inverse is supplied to avoid a full historical state copy. This is not permission to omit clipping or accept stale-gradient training. Finite-precision rollback stability, rare-event failure frequency and broad optimizer support are not established by the reported throughput table.
- §5.1: Megatron-LM-based GPT-like models, up to 32 A100 SXM 80-GB GPUs on four RoCE RDMA nodes; sequence 1024; end stages have one fewer Transformer layer to offset embedding/loss work. Hardware bandwidth value is unreported. Table 3: 1.5B/6.2B/14.6B/28.3B on 8/8/16/32 pipeline GPUs, microbatch size 6/3/1/1 and microbatch counts 3p,4p,8p. 1F1B-I uses each Transformer layer as a chunk. Author correctness check uses identical fixed-seed per-iteration losses, without training to convergence; the reported number of correctness-check iterations is unreported.
- §5.2/Table 4, representative measured row: 28.3B, 32 GPUs, b=1,m=96: ZB-2p 0.99 samples/s/GPU at 74 GB, ZB-1p 0.87 at 44 GB, 1F1B 0.76 at 43 GB, 1F1B-I 0.82 at 58 GB. Doubling an activation budget does not double total memory. Same-activation-cap ZB-1p still has modestly higher measured total memory than 1F1B.
- §5.3/Table 5: bubble rates are schedule calculations using measured timing inputs, not directly measured idle percentages. For the above row: 1F1B 0.2646; ZB-H2 0.0641; ZB-1p 0.1421; ZB-2p 0.0038. Fig. 6 contrasts generated and profiled timelines and acknowledges extra real bubbles. Appendix D/Table 9 supplies timing inputs; its table does not explicitly label time units, so no unit is invented here.
- §5.4/Fig. 7/Appendix B: memory/idle tradeoff plateaus near 2pMB when TF≈TB and Tcomm is small. More memory can have diminishing returns; communication and first-B dependency chains remain.
- §6/Fig. 8: ZB-V maps two chunks/device in a forward-and-reverse V order, enabling earlier local backward and balanced activation demand. Ideal TF=TB=TW permits zero bubble at pMB; actual profiled schedules remain nonzero. Additional chunk boundaries introduce communication and computation-granularity tradeoffs.
- §6.1/Table 6 is the stronger approximately matched-memory/global-batch comparison: ZB-2p* halves b and doubles m, keeping global batch. 28.3B, 32 GPUs, base b=2,m=96: ZB-V 1.01 samples/s/GPU at 71 GB; ZB-2p* 1.00 at 72; ZB-1p 0.94 at 73; 1F1B 0.82 at 69. 6.2B/16 GPUs/base b=6,m=48: ZB-2p* 4.36 at 63 GB versus ZB-V 4.15 at 64; V is not universally fastest.
- Table 7 varies b with fixed m, changing global batch; the b=1→2 14.6B ZB-V row is 1.75→1.88 samples/s/GPU (7.43%). Do not present it as matched-global-batch isolation. Table 8's V bubble rates are calculated, like Table 5.
- Appendix E/Table 10: optimizer post-validation versus allreduce synchronization, samples/s/GPU: 1.5B/8 GPUs/m24 14.5 vs 13.11; 6.2B/8/m24 4.32 vs 4.00; 14.6B/16/m48 1.81 vs 1.68; 28.3B/32/m96 0.99 vs 0.91. No measured rollback-rate sensitivity curve is reported.
- Appendix F/Table 11 keeps listed m while changing b, so global batch differs. It also prints middle m=32 for the 14.6B and 28.3B blocks, inconsistent with the main setup's 64/128. Preserve as a source ambiguity; use Table 6 for fixed-global-batch evidence. Table 11 includes cases where larger-b ZB-1p exceeds ZB-2p, a useful counter-signal.
- Appendix H/Table 12: at m≤p benefits persist but bubbles remain. Example 14.6B,p16,m4,b1: 0.39→0.52 samples/s/GPU, 19→20 GB, 1F1B→ZB-2p. This is throughput at small microbatch count, not elimination of all bubbles.
