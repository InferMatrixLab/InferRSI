## Feature gates and unresolved conflicts

F: [Pinned documented gates L256-L268](https://github.com/Ascend/pytorch/blob/67511c53cd4c88014f6123de7097677e60e85faa/docs/zh/api/environment_variable/memory_management/PYTORCH_NPU_ALLOC_CONF.md#L256-L268) and [source constants L20-L21](https://github.com/Ascend/pytorch/blob/67511c53cd4c88014f6123de7097677e60e85faa/torch_npu/csrc/core/npu/NPUAllocatorConfig.cpp#L20-L21), [parsePinMemoryExpandableSegments L68-L103](https://github.com/Ascend/pytorch/blob/67511c53cd4c88014f6123de7097677e60e85faa/torch_npu/csrc/core/npu/NPUAllocatorConfig.cpp#L68-L103):

- Host expandable segments: documentation says TorchNPU 7.3.0+, HDK 25.5.0+, commercial CANN 8.5.0+. Runtime code bypasses the generic HDK comparison for Ascend950, citing its product-specific commercial versions. Preserve that exception; do not turn it into a universal older-driver allowance.
- Background threads: TorchNPU 26.0.0+ and PyTorch 2.8.0+ per docs. The selected allocator path's support must still be checked.
- Host registration: docs say TorchNPU 26.0.0+, HDK 26.0.RC1+, CANN 8.5.0+. Config's missing-symbol warning agrees, whereas the slow-path feature-not-supported warning says driver 25.5.0. This disagreement is unresolved. P: require documented gates plus actual runtime feature support; do not infer guaranteed support from 25.5.0.
- Round/cache thresholds: TorchNPU 26.2.0+, PyTorch 2.13.0+, default host allocator only; expandable mode warns and leaves thresholds inert.
- [950DT restriction L13-L16](https://github.com/Ascend/pytorch/blob/67511c53cd4c88014f6123de7097677e60e85faa/docs/zh/api/environment_variable/memory_management/PYTORCH_NPU_ALLOC_CONF.md#L13-L16) lists only expandable_segments, pinned_use_background_threads, pin_memory_expandable_segments and pinned_mem_register for that product. Check exact hardware before offering threshold options.
- [environment initialization L44-L63](https://github.com/Ascend/pytorch/blob/67511c53cd4c88014f6123de7097677e60e85faa/torch_npu/csrc/core/npu/NPUAllocatorConfig.cpp#L44-L63) rejects simultaneous PYTORCH_NPU_ALLOC_CONF and PYTORCH_ALLOC_CONF; the alias also has its own version gate. Use a fresh process to compare startup configuration.

## Proposed verification and limits

P: At a later authorized stage, replay a small fixed host allocation/copy sequence under one change in a fresh process. Record host bytes, allocation/free timing, process RAM and correct results at matching stream-completion boundaries. Include a pending-copy ownership case; do not infer safety solely from address reuse. Stop on query errors, output corruption, increased RAM beyond budget or allocation-latency regression, and restore the saved configuration.

P: This bounded read does not establish the installed ATen CachingHostAllocator implementation, whole-pipeline overlap, graph capture semantics, external registration ownership, broad driver compatibility, or optimal thresholds. Pinned reserve-segment internals, host virtual-address exhaustion and fault recovery are outside the selected operational levers.

## Resource scope

RAM / Host: pinned allocation/copy ownership, cache accounting and path/version-gated controls; verification remains proposed. Device HBM, SSD and Network are outside this capability. The two TorchNPU studies share one upstream source, not independent corroboration.
