# Cross-repository mechanisms: ownership, validity and completion

This source-derived synthesis compares nine bounded distillation slices at the
same responsibility layer. Its purpose is to choose the right owner and the
smallest discriminating check, rather than to rank engines or prescribe a shared
runtime abstraction. The [source-scope snapshot](repository-source-scope.md)
retains each source pin, attribution, owner and evidence boundary.

Across these nine slices, native engine/backend, real-model, service and
performance validation is **not_run**. Separately, seven checks passed on
ComfyUI’s unchanged `graph_utils` module; these do not validate its executor, output-cache semantics, model management or accelerator. InferRSI
catalog, package, test and CI results validate knowledge delivery separately.
They do not promote a source-derived candidate. Older, unrelated runtime
evidence retains its original scope and date.

CODE observations below are carried from the linked pinned readsets and
owner-local references. TEST-SOURCE means an assertion was inspected, not run.
Cross-runtime transfer and proposed checks are HYPOTHESIS. No repository-wide
review, compatibility matrix or comparable performance result is established.

and sampling outcomes separate. The complete procedures remain with the

[verification-budget owner](../../../repositories/deepinfer/budget-speculative-verification/SKILL.md).

## Use the existing research procedure

Use this comparison to select a procedure; repository and framework owners
retain the complete operational steps.

1. Select the symptom and responsibility layer, then load the smallest relevant
   source owner from the [coverage table](repository-source-scope.md#per-repository-scope-and-owner).
   Keep SGLang `multimodal_gen` distinct from SGLang-Omni, and MLX array execution
   distinct from MLX-LM request/cache policy.
2. Build one ledger: `identity`, `owner`, `producer`, `consumer`, `validity or
   readiness condition`, `last use`, `terminal/retention event`, `evidence`, and
   `unknown`. Preserve the engine's actual unit: node, array, ubatch, token row,
   component-use interval, stage, request or replica.
3. Trace the selected behavior through setup, normal work, relevant failure and
   cleanup. Check feature-off behavior and effective defaults. Do not assume a
   `finally` covers entry/setup that precedes its `try`, or that an acknowledgment
   includes separately queued reclamation.
4. Propose one falsifying check using the real selected implementation. Examples
   include a changed external input with the same filename, a partial-ubatch
   abort after proven earlier progress, survivor-row correctness after removal,
   mutable scheduler identity during grouped reuse, or release completion on an
   affected replica. Avoid a substitute allocator, scheduler or model that only
   mirrors the proposed explanation.
5. Keep the outcome at its demonstrated strength. Missing fixtures/backends
   remain explicit `not_run` boundaries. Native correctness, real-model quality,
   and matched service/performance acceptance require their own evidence.
