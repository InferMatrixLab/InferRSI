# Profiler window source audit (read-only)

No active trace was read and no GPU operation was invoked.

AsyncOmni.start_profile/stop_profile call collective_rpc(profile,...), async_omni.py938–980. Orchestrator._handle_collective_rpc (orchestrator.py768–805) constructs stage_pools in native order and awaits each pool/replica serially. Thus all-stage start/stop are not simultaneous. Installed vLLM profiler/wrapper.py395 calls profiler.stop synchronously, then may build/write device-time tables. The default torch tensorboard trace handler is configured at258–266. Export completion in early stages can delay later stages' stop substantially.

Installed vLLM benchmarks/serve.py938 starts profiling and waits for the API before generating workload. Requests finish via asyncio.gather at1081, benchmark_duration is measured1090, and stop_profile occurs1462 after statistics/printing. Therefore delayed stop/export should not enter reported request latency or benchmark duration, but enlarges capture windows. Profiling overhead during execution still affects observed workload latency.

Native Omni raw request timestamps use time.perf_counter (benchmarks/patch/patch.py2943,3025,3228,3415; metric comment3869). These are monotonic seconds, not wall-clock epochs. Chrome trace ts/dur use microseconds relative to a trace base. Installed torch profiler/_cupti_monitor_trace.py18–21 documents Kineto's trimester-rounded baseTimeNanoseconds; timestamp conversion subtracts base_ns and divides1000. To align retained trace epochs, use each file's explicit baseTimeNanoseconds/1e9 + ts/1e6; do not assume ts itself is Unix epoch or that all files share a base. Require field presence/units and plausible validation; do not silently invent a missing base from current time.

To align requests precisely additionally requires a paired wall_clock/perf_counter bridge from the same host during that run, ideally sampled before and after with sandwich uncertainty. Current run-profile-v6 phase start_wall_time/end_wall_time bracket the benchmark subprocess, including warmups/profiler lifecycle and export. They provide only broad bounds. Benchmark date is insufficient precision; a wall-minus-perf measurement taken now is only an explicitly qualified approximation, vulnerable to wall adjustments. No exact request-window alignment is established by the current stored phase boundaries alone.

The stage kernel first-start/last-end envelope excludes pure trailing export silence, so a minute of CPU-only JSON writing does not automatically reduce that busy fraction. However any later GPU kernel (background service work, profiler-related device work, pending cleanup) can extend the envelope and/or contribute busy time. Source inspection alone cannot prove absence. Per-process trace scope also does not establish device-wide isolation: another process can contend without appearing as a kernel in that worker's trace. NVML ownership snapshots are complementary coarse observations, not continuous activity traces.

When completed traces are available, report kernel union and envelope separately from full capture span; inspect the tail and kernel/API correlation before attributing it to request work. Include memcpy/memset separately if measuring all GPU activity. Combine intervals only on the same logical device after timestamp normalization; Talker and codec overlap cannot be summed. A stage trace's idle gap need not mean device idle. Exclude clear export-only CPU events, but do not silently prune unexplained GPU tail activity or assert request identity without mapping evidence.

Until a trustworthy request-clock bridge or unambiguous workload markers exists, label results process/stage diagnostic kernel-envelope utilization, not formal GPU utilization, service critical-path fractions, request latency decomposition or available speedup. First/last-kernel envelopes can omit request startup/drain and exaggerate apparent utilization. No source-only conclusion about background GPU contamination is justified.
