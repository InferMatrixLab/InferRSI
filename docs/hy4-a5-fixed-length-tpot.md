# Measuring Hy4-Flash-FP8 decode at a fixed context length

The eight-device Ascend 950DT campaign uses LongBench v2 for decode latency and AIME2026 for answer quality. The latency client issues one request at a time. The current EvalScope accuracy run uses a batch size of sixteen for all thirty problems. The acceptance issue records the image, checkpoint, deployment arguments, comparison gates and measured revisions. [Campaign and round ledger](https://github.com/InferMatrixLab/InferRSI/issues/613)

## Replaying identical prompts

Render each pinned LongBench ID with the published zero-shot template and the checkpoint tokenizer, with no added special tokens. Use the tokenizer offsets to locate the tokens wholly inside the document. Keep the instruction prefix, question, four choices and any tokens that overlap a document boundary once. Fill the remaining positions from the start of the document token sequence, cycling that sequence when more tokens are needed. This produces a deterministic token array and keeps the question at the end even when the document exceeds the budget. All twenty original prompts in this campaign required padding.

At freeze time, record the ordered request file digest and each resized token array's digest. Keep that input read-only for the campaign. Send those IDs directly to the completions endpoint in the published order. On each response, check the API-reported prompt length, generated-token count and completion reason. A change to the dataset, template, tokenizer or storage copy calls for a new identity check. [Input identities and reconstruction rule](https://github.com/InferMatrixLab/InferRSI/issues/613#issuecomment-7120848813)

## Measuring speculative output

Use a monotonic clock on the host loopback client. Record the timestamp and number of generated IDs in each SSE token event, along with the final usage receipt. Divide the interval from the first token event to the last by the actual output length minus one. Compute the median of the twenty per-request values with equal request weights. Keeping time to first token, chunk sizes and the stream completion timestamp makes a change in output buffering visible.

On an exclusive service, take snapshots of the engine's draft-round and accepted-draft-token counters immediately before and after each formal request. Dividing the client decode span by draft rounds gives an approximate round duration. Tokens delivered per round expose variation in acceptance. The two estimates help determine whether to investigate proposal/verification cost or acceptance. A rank-local diagnostic profile from an AIME decode can identify operators for investigation. A fixed-length performance trial is still needed to quantify any effect on the latency objective.

## Comparing revisions

Use one service identity for a round's warmup, formal timing and conditional AIME scoring. Apply the declared latency gain before invoking the expensive evaluator. Retain all predictions, and count a quality reference only when all thirty items have a completed evaluation. Preserve interrupted measurements with their original protocol and completion counts. A new service replays the selected revision, identical request bytes and scorer for the final check. [Service-reuse campaign lifecycle](service-reuse-campaigns.md)

The original fixed-length baseline used serial AIME requests and scored all thirty problems correctly. The predictions contained 208,954 generated tokens, including one answer of 46,582 tokens. Every response ended with the model's stop condition. Audit the submitted user prompts in dataset order and sum the individual accuracy judgments before comparing the result with the aggregate report. This also distinguishes a completed run from a partially written predictions file. [Baseline quality audit](https://github.com/InferMatrixLab/InferRSI/issues/613#issuecomment-7121945182)

The service-reuse measurement receipt carries all twenty request IDs, token counts, TPOT values and their median. Use that receipt and the same service's EvalScope result for routine round reporting. Keep raw timing and predictions available for investigating anomalies. The first candidate spent 1.47 seconds in precheck, 237 seconds reaching readiness, 46 seconds warming up and 620 seconds timing twenty requests. Queue a prepared candidate at service cleanup. Reserve separate model launches for a diagnostic that can change the next candidate choice.

EvalScope connects to the loopback service with a locally frozen dataset. Launch that client with loopback proxy bypass and clear inherited proxy variables in its process environment. A SOCKS proxy inherited from the SSH host prevented the original client from sending its first question. The full retry used a fresh service for warmup, timing and scoring. [Scorer repair and retry](https://github.com/InferMatrixLab/InferRSI/issues/613#issuecomment-7122220240)

When the accuracy concurrency changed to sixteen, two earlier EvalScope runs on the same baseline revision provided matching 30/30 references. Their image, checkpoint, AIME input bytes, scorer, generation settings and model-serving arguments matched. The earlier latency workload and HTTP port differed. Reuse those accuracy results for the new threshold and keep the fixed 127K timing baseline. The incomplete serial candidate's predictions stay in its original attempt. ## Locating a context-limit stall

With the combined input and output exactly equal to the serving context limit, aggregate TPOT hides where the delay occurs. All twenty fixed-length requests completed on the baseline service. Their P50 was 11.4392 ms/token. For each request, take the maximum SSE gap after delivery of at least 1,008 tokens and the maximum from tokens 32 through 1,007. The medians of those maxima were 637.57 ms and 46.11 ms, respectively. The raw timestamps preserve both intervals in the formal TPOT. This observation motivated testing extra serving-context capacity while replaying identical inputs and output caps. [Per-request baseline and hypothesis](https://github.com/InferMatrixLab/InferRSI/issues/613#issuecomment-7121157226)

Reserving 512 extra positions reduced median TPOT to 9.4807 ms/token. The same service answered 29 of 30 AIME problems correctly at concurrency sixteen. The missed response ended normally after 16,171 generated tokens. The original quality comparison rejected the change. [Per-request timing and first quality verdict](https://github.com/InferMatrixLab/InferRSI/issues/613#issuecomment-7123314085)

The operator subsequently set an absolute minimum of 28 correct answers and selected the extra context headroom. The new campaign decision retained the prior service identity, timing and all thirty scores. InferRSI rechecked the recorded warmup, measurements, quality, cleanup, parent and numeric gates. The original decision remains available with its original policy. The selected parent for subsequent trials has a 131,584-position serving limit. [Revised gate and selected deployment](https://github.com/InferMatrixLab/InferRSI/issues/613#issuecomment-7123816356)

## Attributing a change in speculative latency

Record both proposals per verification and serving-context capacity in the parent comparison. A separate run using seven proposals at the original context limit measured 10.3764 ms/token and scored 29/30. The selected five-proposal run with extra context headroom was faster. Keeping these observations on their respective parents prevents attributing the headroom gain to a wider draft. [Original-context comparison and all twenty timings](https://github.com/InferMatrixLab/InferRSI/issues/613#issuecomment-7123586763)

Before timing a new sparse attention path, compare its serving helper against the original paged QK, softmax with the trained sink, and probability/value computation. Include shuffled physical pages, causal subsets, short dense histories, partially active verification blocks and padding-only blocks. Compare the captured helper at the deployed query width and recalled-row count. Register model-owned settings with the Ascend configuration parser so that the normal serving entry point accepts them. [Production-helper checks and launch evidence](https://github.com/InferMatrixLab/InferRSI/issues/613#issuecomment-7124339768)

In this trial the median time per draft round, estimated from the client decode span and engine counters, fell from 39.04 to 37.68 ms. Delivered tokens per draft round changed from 3.915 to 3.766 across the cohort. Each of the twenty greedy completions differed at one or more output positions. The formal median TPOT improved from 9.4807 to 9.0628 ms/token. Evaluate answer quality on the same service before accepting the change. [Per-request timings and draft counters](https://github.com/InferMatrixLab/InferRSI/issues/613#issuecomment-7124646381)
