# Full and short catalog retrieval on two decision pilots

The short catalog exposed all 136 candidates and cut the selector's measured input by **76.4%** across the two pilots. It delivered **0/4** prespecified evidence passages. Original-query Find with the native main reader delivered **3/4**. These two public engineering pilots support a prompt-budget improvement. General retrieval quality and task benefit remain **INCONCLUSIVE**. [Issue and evaluation design](https://github.com/InferMatrixLab/InferRSI/issues/529)

## Paired model calls

Each pilot used its own primary task, original question, known conditions and two blocking questions. The selector independently chose up to three sources in every arm. Find supplied its top five locally. Find with a follow-up pooled the original and one frozen derived query, deduplicating the two top-five lists. The other arms supplied every full or short card in the same snapshot. The arms ran sequentially in reverse order for the second pilot. No external channels were enabled. [Pilot questions, queries and scoring passages](pilots.json)

Each score counts subquestions for which a declared passage (or listed alternative) appeared in a delivered resource. The model never saw the scoring passages as labels. These are author-specified pilot markers and can miss equivalent evidence. The benchmark measures source delivery. It did not grade a downstream answer, a local TTS regression or compatibility on the target deployment.

The table uses schema-constrained responses. The four discovery arms each made one new call per pilot. The native rows replay the same Find choices on parent main using pinned, paginated bodies and declared linked documents. This controls for selection when comparing readers. The shared PR reader used the same question plan, 65,536 direct bytes, one hop, five expansions and 32,768 expansion bytes in all four arms. Each token count comes from the model server and includes task instructions and chat framing. [Measurements, selections and exact evidence locators][pilot-results]

- On TTS, both catalog arms repeated a ref. The interface rejected those responses. Original-query Find supplied a usable quality record. The follow-up pool contained additional relevant sources, but its selector also repeated a ref.
- On migration, the short arm chose three Ascend diagnostic skills and missed the release-specific source. Both Find arms chose the release source. Main could page its primary procedure within budget and delivered the upstream version and A2 scope passages. With the same choices, the PR reader spent its direct budget on other required resources and omitted the complete release procedure. The full-catalog reply again repeated a ref.
- The TTS and migration calls used 23.46 / 24.27 seconds through the full-catalog interface and 20.58 / 20.23 seconds through the short-catalog interface. Each cell is one wall-clock observation, including per-query preparation, inference and completion where valid. The shared corpus and first snapshot were built before timing. Response lengths and validity differed. These timings do not establish a latency speedup.
- The initial plain-JSON run used the same eight arm/pilot pairs. Four responses used translated labels or prose in the purpose enum and four exhausted the output cap before producing valid JSON. All eight yielded zero delivered passages. The complete second run constrained JSON shape, reference membership, question strings and purpose, and still applied the production duplicate-ref check. Both sets of outcomes are retained.

## Budget and ordering checks

On the ten previously frozen queries, the whole selection transport used **80,651–80,670** `o200k_base` tokens with full cards and **20,389–20,408** with short cards. At a 32,768-token window with 4,096 reserved, full cards fell back to Find on 10/10 and short cards fit on 10/10. The shared snapshot contained 81 skills, 48 records and 7 cases. These ten checks measured representation cost without model calls. The counts use a different tokenizer and message boundary from the model table. [Per-query results][pilot-results]

For the two published TTS record refs, both submission orders delivered both direct records (6,053 bytes). With the old ordering, only the timing-first permutation delivered the guide defining the first received delta, decoded packet and audible speech. With timing as the first priority, **both permutations delivered that passage**, spending 17,749 expansion bytes in each. This fixed-selection comparison isolates allocation after the decision. ## Reproduction

The model run used the corpus on integration parent `7626c58` and candidate `24e095a`. All eight schema replies were replayed on `faca670` after adding pinned paths to omission records. Validation outcomes, delivered bytes, omission counts and scored passages agreed. The single Ascend NPU served Qwen2.5-VL-3B-Instruct in text-only mode with vLLM 0.30.0, eager execution, a 126,976-token context and prefix caching disabled. It used temperature zero, seed 529 and at most 768 generated tokens per call. Model shard and tokenizer hashes are in the results. The schema experiment uses the same model and source snapshot as the plain-JSON experiment.

Install the candidate and `tiktoken`, then run the following with a local vLLM chat endpoint serving those weights. On an NPU host launch the server inside `npu run --gpus 1 -- ...` and keep that reservation through both runs.

```bash
review=docs/reviews/catalog-selection-529
python "$review/benchmark_pilots.py" --endpoint "$ENDPOINT" --model "$MODEL_ID" \
  --format json --output plain-run.json
python "$review/benchmark_pilots.py" --endpoint "$ENDPOINT" --model "$MODEL_ID" \
  --format schema --output schema-run.json
PYTHONPATH="$MAIN_CHECKOUT/src" python "$review/read_find_controls.py" schema-run.json
```

The ten-query check calls `prepare_catalog_selection` with each query in `queries.json`, `projection="full"` or `"short"`, `token_budget=32768`, `reserved_tokens=4096` and `len(tiktoken.get_encoding("o200k_base").encode_ordinary(text))` as the counter. The order check replays the two record choices with and without the explicit timing-first priority under the byte budgets above.
