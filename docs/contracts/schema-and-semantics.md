# D017 — Complete v1 envelope specification, canonical encoding, and semantic checks (aligned with the D023 errata)

Status: **Proposed**. Machine fields are authoritative in `schemas/contract-v1.schema.json`: JSON Schema Draft 2020-12, 106 named definitions. Every field on a new fixed object is required; unknown fields are rejected. Nullability is expressed with `null`; a missing field must not create a second reading. `Parameters` is an intentional task/config extension slot, not a quiet permission for arbitrary object fields. See [README.md](README.md) for repository-wide status and dependencies.

The D023 errata (see `p0a-contract-errata.md`) changes this file in a bounded way: `CommandStep` gains a required, nullable `expected_code_sha256`; the prepare closure is delivered in-process; `DeliveredContext` is tightened to a committed record and the draft is a process-local value; the assess primary-claim check order is fixed; and CLI attempt save plus disconnect replay are fixed. V01–V30 are all retained. V31–V35 are added to carry D023. Historic archived outputs are not rewritten.

## 1. Scope, and unchanged legacy formats

- New `PreparedEvaluation`, `ExecutionSpec`, persisted `ExecutionRecordPayload`, `EvidenceInput`, and `EvaluationResult` use integer `schema_version: 1`. The v0.3 `schema_version: str` was an unimplemented sketch; this revision explicitly chooses an integer. It is not claimed that production old v1 data was already integer, or that historic data has been converted.
- `PreparedRef` / `AssessmentRef` likewise use `version=1`. A `RecordRef` version is `record_version` (starting at 1); the payload itself has a separate `schema_version`. The three Ref types are not interchangeable.
- Legacy Knowledge logical records, Bundle manifests/revisions, the old RunSpec / `evaluate` / native Python return values, and the old CLI still use their existing protocols and encodings. Old floating-point or arbitrary-key records are not forced into the new canonical encoding. In Knowledge DTOs, `logical_record` / `bundle` are explicit `LegacyJSON` pass-throughs. Their validation stays with the existing K Bundle / Reader / Store and **is not in the `inferrsi-json-v1` digest domain**. That pass-through slot must not carry unknown fields of a new Execution / Prepared / Result object. `DeliveredContext` archives only an `ArtifactRef` to bytes that were actually delivered; it does not re-encode old logical-record JSON in order to recompute a Bundle hash.
- First-wave `TargetRequest.executor_kind` supports only `local_cpu`. An unknown executor, schema, task, or rule is an explicit `UnsupportedOperation` / `UnsupportedSchema` / `UnsupportedRuleVersion`; a nearby capability is not guessed. New policy for telemetry, real Agents, remote execution, or video is not a prerequisite for K01 / H01.

JSON Schema reference reuse is a documentation structure. It does not authorize K, H, or B to import one another's DTO implementations or to share a business package.

## 3. Exact rules for canonical encoding and identity

These follow D002 and make explicit: ASCII keys in dictionary order; UTF-8 with no BOM, trailing newline, or trailing space; arrays are not freely re-sorted; Chinese is not escaped and is not Unicode-normalized. Duplicate keys, lone surrogates, and floating-point tokens / NaN / Infinity are rejected. Integers are in `[-9007199254740991, 9007199254740991]`; counts are non-negative. JSON Schema's mathematical integer may accept `1.0`, so a **strict byte parser must first reject any floating-point token** and must not rely on jsonschema alone. Non-integer numbers are `Decimal`-defined canonical decimal strings. Negative zero, exponents, and superfluous zeros are rejected; they are not quietly repaired into fixed bytes after a parse.

String escaping does not depend on a language library default: a double quote is written only as `\"`, a backslash only as `\\`. U+0008 / U+0009 / U+000A / U+000C / U+000D are written only as `\b` / `\t` / `\n` / `\f` / `\r`. All other U+0000–U+001F are written only as lowercase four-digit `\u00xx`. Every other legal Unicode scalar is raw UTF-8 (including solidus `/`, U+007F, U+2028 / U+2029, and non-BMP characters) and is not written as `\/` or an extra `\u` escape. Invalid UTF-8 and lone surrogates are rejected; U+FFFD is not substituted. Keys and values use the same escape rule. Keys remain ASCII-only and are sorted by the unescaped string's ASCII code points. Byte parsing first checks duplicate keys, legal Unicode, and the ban on floating-point tokens, then compares with a re-encode under this specification, byte for byte. Alias escapes may appear in ordinary JSON request input, but they must not masquerade as an already-fixed canonical payload. Encoding is locale-independent. `true` / `false` / `null` are lowercase. Integers are decimal with no leading zeros. `-0` in fixed bytes is not canonical.

A `sha256` field is 64 lowercase hex digits. A semantic id is `sha256:<64hex>`. `ArtifactRef` has four fields: `location`, `sha256`, `size_bytes`, `media_type`. `location` is relative to an authorized storage namespace. Absolute paths, drive letters, backslashes, NUL or control characters, `.` / `..`, a repeatedly normalized path, and unsupported links are rejected. `cwd` may be `.`; other paths may not. A raw source path in `SourceSpec.controller` / `target` may be a source under authorized configuration; the `ArtifactRef` path restrictions above must not be mis-applied to an already-accepted input source. An arbitrary network location must not be resolved from `source`.

Projection P is defined as follows: walk the named definitions and field paths of this machine schema recursively; delete `location` only when that field's schema is explicitly declared as `ArtifactRef`, and keep `sha256` / `size_bytes` / `media_type`. An arbitrary object inside `Parameters` / `JsonValue` must be kept in full even if it happens to have the same four fields; a Ref must not be guessed from shape. All original fields of other objects are kept. A role is still retained on the parent `Resource`. Apart from the explicit exclusions in the table below, fields must not be otherwise ignored. `JsonValue` task parameters enter their semantic domain in full.

| Identity | Exact input / exclusions | Hash |
| --- | --- | --- |
| `protocol_digest` | P(`ProtocolV1` with `display_notes` removed) | `sha256` of the canonical bytes, with a `sha256:` prefix |
| `prepared_id` | P(`PreparedEvaluation` with `prepared_id` / `created_at` / `display_notes` removed) | Same; `protocol_digest` is computed first; the protocol byte digest is still kept |
| `request_digest` | The complete `ExecutionSpec`, with no outer receipt (`ExecutionSpec` itself has no `request_digest` field) | Hash of the full canonical bytes, with prefix, including real `location` values so this request's sources are fixed; **includes every `CommandStep.expected_code_sha256` (D023-2)** |
| `RecordRef.artifact.sha256` | Complete `ExecutionRecordPayload` bytes | Hash of the original canonical bytes, with no prefix; `record_version` and `recorded_at` participate |
| `assessment_id` | P(`EvaluationResult` with `assessment_id` / `assessed_at` removed) | Semantic hash; claims, metrics, eligibility, comparison, reasons, and fixed supporting material all participate |
| `PreparedRef` / `AssessmentRef.artifact.sha256` | The complete respective payload, including its own semantic id | Hash of the complete canonical bytes; the outer Ref is not included |
| Raw evidence / directory files | The original actual bytes | Not rewritten canonically. The directory manifest itself follows the new v1 rules |

`ProtocolV1.worker_recipe` carries the measurement semantic version, code identity, and parameter template, and enters `protocol_digest` as frozen rules. `PreparedEvaluation.recipe` is an exact copy of it and is not an independently mutable rule source. A recipe must not freeze a concrete candidate id or hash, this attempt, or an absolute install path; inputs and outputs are bound with fixed role placeholders. A concrete `CandidateExpectation` object lives only on the prepared object, not on the protocol. `ExecutionSpec.InputSpec` keeps this call's binding expectation and is constrained by V28; it is not an independent authority that can replace the frozen expectation. Therefore T21, same protocol and different candidates, has the same `protocol_digest` and a different `prepared_id`.

**D023-1 projection boundary:** P strips only the `location` of an outer, schema-declared `ArtifactRef`. After a complete commit, a new process can read using only the fixed Ref and the same configuration. Committed bytes are immutable. This **must not** be taken to mean that an arbitrary relocation leaves `prepared_id` unchanged: if the canonical bytes of the protocol object or of a resource description itself change because of an **internal field**, the corresponding sha and `prepared_id` are recomputed under the original rule.

Collection rules: `Resource` items are uniquely sorted by role; input collections are uniquely sorted by role; `DirectoryManifest.entries` are uniquely sorted by path. `steps` / `samples` / `args`, claims, metrics, and result arrays that have a semantic order keep the order defined by the protocol and are not generally sorted. The order of `claim_definitions` is the order of result claims (each key is unique). `required_evidence` is unique on `(check_id, checker_revision, subject, phase)`, frozen in the protocol's declared order, and is identical between the protocol and the prepared copy. The P1 fixture's required order is an explicitly frozen order; already-fixed bytes are not auto-sorted on read.

### D023 added checks (V31–V35)

| ID | Required check / unique failure |
| --- | --- |
| V31 | **Prepare in-process closure (D023-1).** B's `prepare` return must, in addition to the `PreparedEvaluation` object, provide both (a) the canonical bytes of the protocol frozen for this call, consistent with the sha/size of `prepared.protocol`, and (b) a read-only entry (bytes or a stream) to the resource closure, keyed by role, covering every role in `prepared.resources`. Existing, verifiable resources may reuse an existing reader. **A newly generated protocol must not supply only an as-yet-unresolvable `ArtifactRef`.** Under a trusted, explicit `StorageConfig`, Apps allocates the final location, then checks the final prepared canonical bytes through B's pure `encode` / `validate_prepared` (which may accept an already-allocated location) before archiving. After a complete commit, a new process can read using only the fixed Ref and the same configuration. Identity strips `location` only under projection P. An internal-field change must recompute the sha / `prepared_id` under the original rule. |
| V32 | **Frozen code digest (D023-2).** `OperationRecipe.code_sha256` is the frozen expectation. Scope is a supported entry or package; the whole interpreter is not archived. Every `CommandStep.expected_code_sha256` field must be present. In evaluation mode (`prepared_ref` non-null) its value **must equal** `prepared.recipe.code_sha256`. `OperationRecipe.code_sha256` is already a required non-null `Sha256`, so there is no “recipe omitted a code digest” branch. Apps maps the value verbatim from the fixed `prepared.recipe` and must not rewrite or infer it. In ordinary command mode (V05's five fields all `null`) it must be `null`. A spec-time violation (ordinary command mode with a non-null value, or evaluation mode with `expected` `null` or not equal to the frozen `recipe.code_sha256`) is refused as `InvalidExecutionSpec` before registration: no start, no record, and it must not be treated as T37. A missing required key is refused first at the schema layer; a schema-validator failure must not be equated with `InvalidExecutionSpec` or any other runtime `PublicError`. T37 applies only in evaluation mode, after `expected` already equals the frozen recipe, and only to the pre-start check of actual entry bytes: if the actual digest differs, there is zero start and a `not_started` submit (a submit failure follows the existing `ExecutionPersistenceError`); if the actual entry cannot be resolved, record `not_performed`/unknown and do not fabricate a mismatch. Ordinary-command null mode does not cover T37. H computes and checks the actual entry-byte digest before the candidate process starts, and does not import B. `expected_code_sha256` participates in `ExecutionSpec` canonical bytes and `request_digest`. Introducing this field must update the schema, the V checks, and the `ExecutionSpec` / `request_digest` goldens together, and **must not rewrite historic archived outputs**. An equivalent projection (for example a versioned H read-only binding projection that reads the same expectation from the fixed prepared object) must state that equivalence in the same contract revision, and must not record only the actual observation without checking the expectation. |
| V33 | **Delivery context (D023-3).** The `DeliveredContextDraft` returned by `ContextProvider.collect` is a process-local value and **must not carry an as-yet-uncommitted valid `ArtifactRef`**. Its bytes or stream, intended logical location, and digest are draft facts only. After H finishes retention with its own capture and commit, it seals the final `DeliveredContext` (whose `artifact` points at already-retained bytes) and only then writes the generation manifest. The writer is always H; Apps does not write H's RunStore directly. On a retention failure, no valid delivery Ref may be published. After a successful commit, a new process with the same configuration can read exactly the same actual delivery bytes as the draft; it must not keep only a reference and then report `ArtifactUnavailable`. `DeliveredContextDraft` is not a JSON DTO; no serializable stream shape, and no fabricated one-shot JSON stream, may be invented for it. |
| V34 | **Primary-claim check order (D023-4).** `AppsResultV1` must include `primary_claim_id`, `primary_scope`, `exit_code`, and `error`, and must keep inner/outer Ref and `admission` consistent. `assess` must be given an exact `(primary_claim_id, primary_scope)`. ## 6. Task-owned concrete syntax and rules of the P1 fixture protocol (not imposed on a real task)

Registry keys: `task=p1-fixture@1`, `grader=p1-rules@1`, `assessor=fixture-assessor@1`, `operation=evaluate`, top-level `scope=p1`. Parameters are closed-validated by `P1Parameters` (`decimal_fixture` and `label` are only fixed content for this encoding-test protocol, not a performance-gain threshold). This does not claim that a real task library has been implemented. The protocol's required `format-proof` / `grader-proof` / `samples-proof` / `cleanup-proof` correspond to `P1FormatProof` / `P1GraderProof` / `P1SamplesProof` / `P1CleanupProof`. An unknown version is explicitly refused.

- F: matches this candidate's actually captured sha / attempt / operation / scope, a trustworthy format check, and the fixed schema. A trustworthy `failed` → F FAIL. A trustworthy `passed` whose unique required condition holds → PASS. Missing, bad bytes, foreign, conflict, or a source that does not meet the requirement → INCONCLUSIVE. A “passed” filled in by the candidate itself is not an independent check.
- C: likewise uses a matching trustworthy grader proof. `failed` → C FAIL; a complete trustworthy `passed` → PASS; otherwise INCONCLUSIVE. An independent FAIL is not overlaid because M lacks samples or cleanup is unknown.
- M: this run did execute, and a complete valid samples proof in the frozen order A1/B1/B2/A2 (two rounds AB, BA), with matching round/role, all values positive `Decimal` and `unit=ms`; the record completion conditions, cleanup, and resource release are all confirmed, and a trustworthy cleanup proof agrees with the record — only then is M PASS. Any missing item or conflict → INCONCLUSIVE. M is measurement validity, not a performance-gain PASS. This fixture has no unified gain total.
- If the same scope has two mutually contradictory proofs and the protocol has no special case that can decide them, that claim is INCONCLUSIVE/conflict; seeing `fail` first does not swallow the conflict. T05/T06 supply one sufficiently trustworthy independent error proof and no contrary evidence; their FAIL does not generalize to every task.
- In the P1 schema, `candidate_id` / `actual_sha256` are declarations in checker output awaiting verification. They are usable only after they have been checked against the fixed record `BoundInput` and the actual capture route; they do not prove themselves. T25, where the record's actual candidate sha differs from expected but there is no format or correctness error proof, does not invent a mathematical FAIL.
