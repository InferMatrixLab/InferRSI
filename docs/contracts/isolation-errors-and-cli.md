## D020 — The first Knowledge slice must move together; seven pure shells must not be claimed as already-proven compatibility

> D023 does not touch D020. The text below is retained.

### 1. Minimal, determinate split of catalog's mixed duties

A narrow check of the same-SHA original confirmed that `catalog.repository_pack` only validates the existing `REPO_TYPES`, then `json.loads` after reading `data/repo_packs/<repo>/pack.json` via `files("inferrsi")`. `infra.inspection` is an existing consumer (original import at L10, call at L56). It is not Knowledge corpus reading, and it is not target selection or executor policy.

The decision is a neutral technical leaf `src/inferrsi/_repo_pack_data.py`. It holds **only the original `REPO_TYPES` static tuple and the original `repository_pack` raw-data reader**. Original signatures and annotations (`dict[str, Any]`), errors, package anchor, and values stay the same. `typing.Any` and future annotations must be kept; signature types must not be deleted to narrow a allowlist. Only stdlib `json` / `importlib.resources` / `typing.Any` and the original future annotations are used. It does not import K / H / B / Apps / infra, does not filter devices, does not create targets, and does not score. `K.catalog` takes the existing data enumeration from this leaf only, and **does not export `repository_pack` as a new K public API**. Root `catalog` re-exports K symbols as a pure static shell, and also re-exports `REPO_TYPES` / `repository_pack` from this exact leaf. In the same PR, `infra.inspection` changes that one import to this leaf. It must not load K by passing through the catalog shell, and it must not be turned toward H (which would create infra→H). Interpretation of a new H target and capability policy still belongs to H; sharing a raw reader does not transfer ownership. The eventual `pack.json` resource belongs to H; K does not read it.

The three `REPO_TYPES` access paths must be the same tuple object. Derived `KNOWLEDGE_SCOPES` / `KNOWLEDGE_REPOS` values stay unchanged.

This is not a fourth core or a shared business DTO, and it is not a legacy classification that skips review. The technical leaf's allowed imports and symbols, the single infra import change, and catalog's two exact export paths are listed together in the P0b formal review and the static transfer graph. The leaf's exact imports, two symbols, top-level shape, and original source fragment and hash are already written into the manifest in structured form. The new file does not exist yet; the complete file hash is locked at ordinary K01 review and is not fabricated. A K02 resolver change must review a revision of that manifest separately and must not silently widen the surface. The new K public closure may use only this business-free technical leaf and the canonical encoder; it may not use them to add other business. Rejected: moving the whole catalog, including target descriptions, into K; catalog→H and then letting infra load H through catalog; copying two sets of `REPO_TYPES` / read business; keeping a mixed catalog business body while calling it a pure shell; migrating the whole `infra.inspection` module in order to enlarge the first wave.

## D021 — Closing semantic gaps, Reader routing, and a stable error table

> D023 does not change this section's Router, error table, or re-entry table. **D023-1 supplement:** `prepare` must, in addition to `PreparedEvaluation`, deliver the protocol's canonical bytes and a read-only, role-keyed entry to the resource closure. Apps reuses this section's `StorageConfig` routing to allocate the final location. **D023-3 supplement:** `DeliveredContext` must have retained bytes and a commit before there is a valid Ref (see V33). **D023-2 supplement:** the observed-actual meaning of `RuntimeBinding.code_sha256` is in V32. This section's item 1 candidate-expectation constraints are unchanged.

### 1. There is only one constraint set for candidate expectations

V28 is normative. Declaration equalities are verified before registration by Apps field adaptation and the identity guard at H's execute entry. H uses its own defined v1 read-only binding projection to parse the fixed prepared identity fields (id / digest / operation / scope / expected). It does not import B DTOs or code, and it does not interpret task format rules or scoring. Ordinary command mode has no such dependency. A format reference is compared only for identifier equality; actual semantic checks still belong to the frozen B worker / rules. A non-null `expected_candidate` in the prepared object imposes mandatory equalities on `candidate_id`, format, and that role's `InputSpec.expected_sha256`. If declaration A and declaration B disagree → `InvalidExecutionSpec` before registration, no start, no record. If both declarations are A and H actually captures B → a fixed `not_started` record after registration and actual binding (except when the commit itself fails). A prepare with no expectation leaves the original prepared object unchanged. `captured-sha256@1` allows no caller expectation, but H must still capture the actual sha and run the retained copy. `expected-sha256@1` requires a non-null `expected`. An artifact source must also satisfy `source_ref.sha256 = expected_sha256`. B re-checks against the fixed record and does not treat a source original path or a self-reported id as proof.

H `InputBinder` captures actual bytes from an authorized source. If they disagree with the caller / Ref expectation, the actual B may be left as a **new `ArtifactRef(B)`** plus the failure facts, but B must never be passed off as the original `Ref(A)`. An ordinary `ArtifactReader` hash failure must not be treated as “verification succeeded.” When B reads the new Ref it still verifies against the new hash. A recorded check failure is also not “the wrong entire top-level record.”

### 2. Record elapsed time and refusal encoding

Record-level `elapsed_seconds` is the observed duration, measured on a monotonic clock, from a successful claim of this attempt to that payload's **seal measurement point**. It excludes post-seal encoding, disk write, and commit, and it does not define a “time-to-end-of-commit” that cannot be observed inside the bytes themselves. `step.elapsed_seconds` is from actual process start to confirmed end; if never started it is `null`. When pre-start duration was not observed, the record-level value is also `null`; 0 must not fill in unknown. The v2 golden changes `not_started` record elapsed and wall-time usage to `null` / `unknown` / `not_observed`, and every dependent hash is updated together. This remains a documentary vector, not a measured execution.

For an admission or identity refusal that has been registered and never acquired a resource requiring cleanup: `phase=finished`, `process_outcome=not_started`, `started=false`, `cleanup=not_needed`. If a resource was first acquired, `cleanup=confirmed` after release is confirmed; if not confirmed, `phase=recovery_required` and cleanup is unknown or failed. A lease must not be erased in order to unify `phase`.

### 3. Request re-entry and crash-result table (digest first, then state; a free lock is never treated as not-started)

| Already-registered same-key situation | Unique result |
| --- | --- |
| Digest differs | `RequestConflict`; the original request is unchanged |
| `finished` and the commit is complete | Return the original fixed `RecordRef`. Even if the owner is still releasing the lock, do not rerun |
| `recovery_required` / `side_effect_unknown` | `RecoveryRequired`, with `latest_ref` if any; check and clean only, never execute |
| Non-terminal + a valid owner lock | `AttemptInProgress`; do not wait and do not make a new binding |
| Non-terminal + lock free / owner unknown, with no commit or only an old running revision | `RecoveryRequired`. Even a registered row, or an OS lock that has already been released, must not auto-recover or rerun |
| State claims `finished` but the corresponding payload is missing or has a bad hash | `RecordIntegrityError`; do not start |
| Not registered | Atomic claim; a registration failure yields no start for this call |

H01-4 must include a crash after an external side effect and before the record commit. A reopened process that sees a free lock still gets only `RecoveryRequired`. Object writes, the claim transaction, the record transaction, and a lost response are each verified at their crash point. A local SQLite transaction is not an external side effect that is exactly-once.

**D023-5 supplement:** Disconnect replay of the same saved `AppsExecuteRequest` must land in this table: already complete → the original `RecordRef`; unknown → `RecoveryRequired`; no new attempt is allocated, and the deadline or budget is not extended.

### 4. Reader namespaces

`StorageMount.namespace` is a stable local namespace of 1–128 characters matching `[A-Za-z0-9][A-Za-z0-9._-]*`. A UUID may be generated by default, but an explicit `demo` is also legal; once created it must not be quietly changed. `root` must be an explicit, authorized, non-empty local absolute path. `StorageMount.prefix` is a canonical relative path without a trailing slash, such as `archives/demo` or `stores/demo`. A match requires that `location` start with `prefix + "/"`. In one operation's configuration, prefixes are pairwise neither equal nor ancestors of each other. Configuration overlap is `InvalidRequest` before any read. Under a legal configuration, a Ref that does not match is `UnsafeArtifactPath`; a second root is not polled. A directory reader confines the remaining relative segment to the authorized root and rejects links and path traversal. A `harness_sqlite` reader resolves only the original BLOB of a specified namespace, fixed attempt, and version. The namespace must match the last segment of the mount prefix and the store identifier. `root` is a local path from a trusted, explicit `StorageConfig`. A root configuration is not accepted from an `ArtifactRef` or from archived content, and there is no network access. `archive_namespace` / `harness_namespace` in the configuration must each uniquely match a mount. Archive writes must use `directory`. H writes for `execute` must use `harness_sqlite`. Offline assess may replace a read-only store mount with a directory export. Write capability is constructed by Apps and H themselves; a general reader is not upgraded into a writer. An offline export may replace a same-prefix store reader with one explicit directory mount, but two readers must not be stacked at once. Byte, hash, and top-level identity checks are not reduced.

### 5. Finite `PublicError.code` enumeration and mapping (exact case)

| Situation | code |
| --- | --- |
| Non-H input fields are illegal, a result key is repeated, or no legal primary-claim selection is provided | `InvalidRequest` |
| H `execute` declarations of schema, path, expectation, or role are illegal, and the request is not registered | `InvalidExecutionSpec` |
| An explicitly unsupported executor or operation declaration (a registered request that lacks execution capability takes `not_started`, not this code) | `UnsupportedOperation` |
| Unknown major version of a new envelope schema | `UnsupportedSchema` |
| Unsupported frozen task / grader / assessor / identity-rule version | `UnsupportedRuleVersion` |
| After a legal parse, a top-level prepared / record / attempt / operation / scope / semantic id does not match | `IdentityMismatch` |
| Old K CAS / revision inconsistency | `RevisionConflict` (the old native exception and encoding are unchanged; a new adapter may map to this code) |
| Same key, different digest | `RequestConflict` |
| Same key, owner still valid and in progress | `AttemptInProgress` |
| It cannot be proved that the work can be ended safely, or an old non-terminal lock is free | `RecoveryRequired` |
| H registration / object / commit storage failure | `ExecutionPersistenceError` |
| Apps prepared / assessment byte archival failure | `ArchivePersistenceError` |
| H.read `latest` has no commit at all, including a nonexistent attempt | `NoCommittedRecord` |
| H.read specified version does not exist | `RecordNotFound` |
| H's own persisted index / record is inconsistent, or the BLOB is bad | `RecordIntegrityError` |
| A general Reader lacks the bytes or cannot access them | `ArtifactUnavailable` |
| A general Reader opens a declared Ref and the hash or size does not match | `ArtifactIntegrityError` |
| An illegal authorized path or link, or a non-matching or ambiguous mount | `UnsafeArtifactPath` |
| The pure B assessor hits an internal error and has no legal result; **or the B result omits a requested claim key that exists in the protocol (D023-4)** | `AssessorError` |

Error priority: version support first, then field validation for that version, then top-level bytes / identity / semantics; H then does digest / re-entry / admission. H source code classifies a fixed bad spec as `InvalidExecutionSpec`; an unknown schema remains `UnsupportedSchema`. A registered capability, budget, or actual-input refusal is **not** a top-level thrown `AdmissionRejected`; it must deliver a `not_started` record or `ExecutionPersistenceError`. `ErrorFact.code` and each task's reasons keep their versioned namespaces and are not freely mixed as `PublicError` strings. Bad individual evidence inside a correct combination is captured by B as that item being unavailable and is interpreted under the claim rules; `ArtifactIntegrityError` is not promoted to “the wrong whole evaluation.” Only when the top-level protocol, prepared, or record itself cannot be read, so that a legal combination cannot be established, is the call refused and no result produced.

## D022 — Path-by-path retention of old entries, and the concrete new Apps v1 specification

> D023 makes three bounded supplements on top of D022 and **does not change** the compatibility commitments in section 1 or the remaining rows of the exit matrix in section 3. The supplements are: D023-4 primary-claim check order; D023-5 required `AppsExecuteRequest.attempt` and disconnect replay; and D023-2 `CommandStep.expected_code_sha256` synchronized into the `ExecutionSpec` / `request_digest` goldens.

### 1. Compatibility and sequence

K01 / H01 do not implement the new CLI, and they do not touch the console `inferrsi=inferrsi.cli:main`, `__main__`, `arguments.parser` / `Path` / defaults, old root / harness evaluation, old `run` 0 / 1 / 2 / stdout / stderr, `plan` / `--dry-run`, existing grade behavior, or plugin entries. Old `run` judgment still gives incomplete priority over failed, and the arrangement of reasons does not change meaning. Old `evaluate` migration follows D018-B4: `B.legacy_run_v0` keeps the rules, and `Apps.legacy.evaluation` assembles. First the runner detaches from the internal `evaluate`, then the old `evaluation` / `harness.evaluation` compatibility edges are reviewed leaf by leaf. New H must not score through an old shell. That dependency constrains only that later legacy-evaluation slice and does not hold K01 / H01 hostage.

The new Apps design adopts the `prepare` / `execute` / `assess` names and the 0 / 2–9 meanings proposed in #371, but both that issue and #333 **remain Proposed, not already-accepted fact**. To stop Apps inventing an overall verdict when one scope has multiple claims, this revision explicitly adds required `primary_claim_id` and `primary_scope`. That is an author revision of the original draft and must go through ordinary review with the Apps slice; it must not be claimed as full compatibility with the original draft.

### 2. Exact requests and results

The schema adds `AppsPrepareRequest(request=PrepareRequest)`, `AppsExecuteRequest(prepared_ref, proposal, attempt, output_root)`, and `AppsAssessRequest(record_ref, primary_scope, primary_claim_id)`, all with `schema_version=1` and every field required. `StorageConfig` is injected explicitly by a trusted host, does not enter the protocol or candidate hash, and a cancellation signal is a host handle, not a serialized DTO. Apps reads the fixed prepared object to perform role substitution. It does not look up `latest` from a path, and it does not allocate a new attempt or extend a deadline or budget.

The complete `AppsResultV1` field set is authoritative in the schema: `schema_version` / `operation` / `outcome` / `reason_code` / `exit_code` / `primary_scope` / `primary_claim_id` / `attempt_id` / `admission` / `execution` / `prepared_ref` / `record_ref` / `assessment_ref` / `assessment` / `error`. Absence is an explicit `null`. `execution` is the flattened `ExecutionRecord` after a genuinely successful commit, and `record_ref` must equal the Ref inside it. When `execution` is non-null, `admission = execution.budget_admission`, `prepared_ref = execution.prepared_ref`, and `attempt_id = execution.attempt_id`. When `assessment` is non-null, its `record_ref` / `prepared_ref` / `attempt_id` must also equal the outer fields, and a non-null `assessment_ref` must match its id / version / hash. When an operation fails and there is no `execution` / `assessment`, result fields must not be fabricated from the input declaration; partial facts go only in `error.partial_record`. On archive failure, `assessment` may keep the in-memory B result, but `assessment_ref` must be `null`. A prepare archive failure does not invent a `PreparedRef`. An execute error may still list an existing `latest_record_ref` beside it, and must not pass it off as this call's new Ref. `reason_code` only copies `error.code` or is `null`; a task reason is not privately selected. The assess primary key must be the unique exact claim key in the fixed protocol / result; Apps is not allowed to aggregate multiple claims.

CLI: `inferrsi evaluate prepare` / `execute` / `assess`. Each `*-ref` argument uses `@<local JSON file>`, and the file is the complete corresponding Ref, not a location string or a hash. The request argument `--request @<JSON file>` corresponds to the `Apps*Request` above (if execute is also given extra ref arguments, they must equal the request exactly, otherwise `InvalidRequest`). `--storage-config <local JSON config file>` supplies `StorageConfig` explicitly. `primary_scope` / `primary_claim_id` must be present inside the assess request; if the command line also provides `--scope` / `--primary-claim`, they must be the same. The first item must not be selected by default. Ref files are decoded as strict JSON and validated against the corresponding schema. Canonical payload and identity still follow D017 byte-for-byte; the Ref argument file itself is not the payload. Compatible old CLI does not accept or interpret these new flags until a later formal Apps implementation slice is merged.

### 3. Exit / result matrix (0 is not a global PASS)

| Operation / situation (in this table's order) | outcome / exit |
| --- | --- |
| Record commit or archival of the current operation fails | `persistence_error` / 6; no valid Ref for this call; a saved B result and the save error are listed side by side |
| `PublicError` `RecoveryRequired` / `AttemptInProgress` | `recovery_required` / 5; `in_progress` / 4; do not start a new run |
| Any other `PublicError` | `error` / 2; a business FAIL is not fabricated |
| `execute` has committed `phase=recovery_required` | `recovery_required` / 5; the new fixed `RecordRef` is kept, and this is distinct from a re-entry exception |
| `execute` has committed `not_started` | `not_started` / 3; the three budget / binding failure facts stay on `execution`; this is not FAIL |
| `execute` has committed `timed_out` / `cancelled` / `execution_error`, or `exited` with a non-zero `exit_code` | `execution_failed` / 7; this is not a B FAIL |
| Any other complete, supported, normal `execute` ending | `success` / 0; still not a B PASS |
| `prepare` archival succeeded | `success` / 0 and a valid `PreparedRef` |
| `assess` has been archived and the selected exact primary claim is PASS / FAIL / INCONCLUSIVE | `success` / 0, `fail` / 8, `inconclusive` / 9; complete results for other scopes / claims are retained and not overlaid |

`assess` follows only the B result and the archival state. An independent claim is not overlaid by a historic non-zero execution. With no legal primary key the result is `InvalidRequest`, not an Apps choice. Exit 2 keeps a detailed code for ordinary boundary errors. Result-field references must be consistent; the mere presence of a ref is not success. Later unified events are implemented separately under #333; this envelope is not the old event schema. The first wave adds no CLI, so implementing the new names and claim selection is not an extra prerequisite of today's P0 / K01 / H01.

**D023-4 primary-claim check order (replaces this section's “select a claim” implementation detail):** after a legal fixed protocol has been read, first check the requested key with B's public read-only claim-key capability or an explicit business-free projection — key not in the protocol, or no legal primary key → `InvalidRequest` / exit 2; the assessor is not called and no assessment is written; key in the protocol but omitted from the B result → `AssessorError`-class result-contract error / exit 2 (this section's “any other `PublicError`” row maps that code to `error` / 2); Apps does not fill in the claim or mis-report it as a caller argument error; for a legal complete result, archive failure takes priority (exit 6, `assessment_ref` must be `null`); on success, return 0 / 8 / 9 for the selected claim.

**D023-5 CLI attempt save and disconnect replay:** `AppsExecuteRequest.attempt` is required; `execute` no longer calls `allocate_attempt` itself. `StorageConfig` is injected by a trusted host or an explicit `--storage-config` and does not enter any `Apps*Request`. First supported path: the host first calls `allocate_attempt`, saves the complete `AppsExecuteRequest` before execution, and then hands that file to the CLI. Disconnect replay must reuse the original attempt and the original request: already complete → the original `RecordRef`; unknown → `RecoveryRequired`; no new allocation, and no extension of deadline or budget. P0a does not grow the command set; K01 / H01 still do not implement the CLI.
