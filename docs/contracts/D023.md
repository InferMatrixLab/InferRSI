## D023-1 prepare 闭包字节、资源入口与最终 locator

`prepare` 仍不写盘、不占预算、不启动进程。进程内交付在 `PreparedEvaluation` 之外**必须**同时包括：

1. 该次冻结协议的规范字节；
2. 按 role 读取资源闭包的只读入口（字节或流）。已有且可校验的既有资源可复用既有 reader；新生成协议不得只给尚未可解析的 `ArtifactRef`。

Apps 在可信、显式注入的 `StorageConfig` 下分配最终 location，再调用 B 的纯 `encode/validate`（可接受已分配 location）生成并核对最终 prepared 规范字节后归档。Apps 不重写 B 规则；B 不依赖 Apps 存储路由，也不自行存盘。缺任一必需资源、校验或归档失败：无有效 `PreparedRef`。完整提交后，新进程仅凭固定 Ref 与同一配置可读。

身份重算仍遵守既有投影 P：只剥外层已声明 `ArtifactRef` 的 `location`。**不能泛称任意搬迁都不改变 `prepared_id`**；若协议对象或资源描述自身的规范字节因内部字段变化而改变，相应 sha 与 `prepared_id` 按原规则重算。已提交字节不可改写。

机器 schema 对应：`PreparedEvaluation` 不新增存储位置或归档句柄字段；最终 location 只出现在其 `protocol`/`resources[].artifact` 的既有 `ArtifactRef` 中。

**验收 T36。**

## D023-2 冻结 worker 代码摘要必须在启动前到达 H

`OperationRecipe.code_sha256` 是冻结预期。P0a **选定**默认路径：在 `CommandStep` 增加可空 `expected_code_sha256`。

- 评测模式（`prepared_ref` 非空）**必填且必须等于**该冻结值。`OperationRecipe.code_sha256` 在 schema 中已是 required 非空 `Sha256`，不存在「recipe 未声明代码摘要」的第三种情形，因此也不把评测模式下的 expected 写成可空；
- 普通命令模式按 V05 为 `null`；规格期若出现非 null，或评测模式 expected 为 null / 非 null 但不等于冻结 recipe，走 `InvalidExecutionSpec`，不启动、不造 record，不得称作 T37。缺 required key 是 schema 层拒绝，不得把 schema validator 等同运行时 `InvalidExecutionSpec` 或 `PublicError`；
- Apps 从固定 `prepared.recipe` 原样映射，不得自行改写或推断；
- H 在启动前计算实际入口字节并核对，不 import B；
- 代码身份作用域是受支持入口/包，**不归档整个解释器**。

机器 schema 对应：`CommandStep.expected_code_sha256` 字段始终存在（新增 required），类型为 `null` 或 64 位小写 hex 的 `Sha256`；模式等值约束由 V32 承担，schema 不假装能表达跨字段相等。

若后续实现改用有版本的 H 只读绑定投影从固定 prepared 读取同一预期，**须在同一契约修订中写明等价性**，且不得只记录实际观测、不核预期。本卷不把“只能通过一种 DTO 字段实现”写成永久禁令（见末节）。

**验收 T37。**

## D023-3 DeliveredContext 先有字节与提交，后有有效 Ref

`ContextProvider.collect` 不得返回尚未提交的有效 `ArtifactRef`。默认路径：Apps 返回 `DeliveredContextDraft`——items/selection/omissions/limitations、字节或流、拟用逻辑位置与摘要；H 用自有捕获/提交完成留存后**封存**最终 `DeliveredContext`，再写入 generation manifest。允许改为调用 H 定义的捕获端口，但写入者仍是 H。Apps 不直接写 H RunStore。

机器 schema 对应：`DeliveredContext` 是**已封存、已提交**的交付记录，其 `artifact` 只能指向已留存字节。提交前的 `DeliveredContextDraft` 是**进程内（PROCESS-LOCAL）**值类型，故意**不**定义为 JSON `$defs` 条目，也不给它编造一个可序列化流 DTO 的形状；其字节/流是进程内对象，不是 schema 载荷。

**验收 T38。**

## D023-4 主 claim 校验顺序与 AppsResultV1

P0a 文档与 schema 对齐 D022：`AppsResultV1` 必含 `primary_claim_id`、`primary_scope`、`exit_code`、`error`，并保持内外层 Ref/`admission` 一致性。assess 必传精确 `(primary_claim_id, primary_scope)`。

读到合法固定 protocol 后，**先用** B 公开的只读 claim-key 能力或明确的无业务投影核对请求键，不调用 assessor 之前即完成判定：

- 键不在冻结协议，或未提供合法主键 → `InvalidRequest` / exit 2，不调用 assessor、不写 assessment；
- 键在协议中，但 B 结果遗漏该键 → `AssessorError` 类**结果契约错误**，Apps 不补判、不误报为用户参数错误；
- 合法完整结果：归档失败优先（exit 6，可保留内存结果但 `assessment_ref` 必须 `null`）；成功后按所选 claim 返回 0/8/9，其他 claim/scope 原样保留。

机器 schema 对应：`AppsResultV1` 四个字段均为 required（可空但不得缺席）；`AppsAssessRequest.primary_scope`/`primary_claim_id` 为必填 `Id`。

**验收 T39**：在 T35 之上增加「键不在协议」与「键在协议但结果遗漏」两行，结果唯一。

## D023-5 CLI 的 attempt 保存与断连重放

`AppsExecuteRequest.attempt` 必填；`execute` **不再**自行 `allocate_attempt`。`StorageConfig` 由可信宿主或显式 `--storage-config` 注入，**不进入** `Apps*Request`。

首期受支持路径：Python 或宿主先调用 H `allocate_attempt`，**执行前保存完整 `AppsExecuteRequest`**，再把该文件交给 CLI。若以后承诺纯 CLI 独立闭环，再另定义获取该文件的入口，不在 P0a 扩命令集。K01/H01 仍不实施 CLI。

机器 schema 对应：`AppsExecuteRequest.attempt` 为 required 的 `AttemptContext`；`StorageConfig` 定义存在但不被任何 `Apps*Request` 引用。

**验收 T40**：同一 RunStore、同一已保存请求；首次提交后响应丢失，重发放回原 `RecordRef`（已完成）或 `RecoveryRequired`（状态未知）；不新分配、不延长期限/预算。断连重放**必须重用原 attempt/原请求**；禁止把不同请求或超期重跑说成同一次重放。

## 明确不纳入本勘误

- 任意内部 location 变更都保持 `prepared_id`；
- 代码摘要只能通过一种 DTO 字段实现、禁止等价投影；
- 把首批 `prohibited_first_wave` 写成永久禁止，或未经单独 review 写成永久允许壳→Apps；
- 因示意树省略 `views/__init__.py` 断言打包已坏；
- 把断连重放解释成不得复用原 attempt；
- 把 `collect_candidate` 的定位/字节提取升级为已证实的 Apps 判分越界。

## 边界与不变项

- P0b 精确门禁政策仍须正式架构 review 接受后才 K01。
- H01 新建本地 SQLite RunStore，不迁测试 MemoryArchive。
- 不要求整个 Apps 实现完成才能开始 P0a 或搬家。
- 旧 `run` 0/1/2 与既有入口兼容承诺不取消。
- 本卷不新增永久门禁豁免；任何门禁政策变更须走 P0b 正式 review。
