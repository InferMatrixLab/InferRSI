## D021 — 语义缺口闭合、Reader路由与稳定错误表

> D023 不改变本节 Router/错误表/重入表。**D023-1 补充**：prepare 必须在 `PreparedEvaluation` 之外交付协议规范字节与按 role 的资源闭包只读入口；Apps 复用本节的 `StorageConfig` 路由分配最终 location。**D023-3 补充**：`DeliveredContext` 必须先有留存字节与提交，才有有效 Ref（见 V33）。**D023-2 补充**：`RuntimeBinding.code_sha256` 的实际观测语义见 V32；本节第 1 条候选期望约束不变。

### 1. 候选期望只有一套约束

V28是规范：声明等式由Apps字段适配和H执行入口的身份guard在登记前验证；H用自己定义的v1只读binding投影解析固定prepared的身份字段（id/digest/operation/scope/expected），不import B DTO/代码，不解释任务格式判据或判分，普通命令无此依赖。格式引用只作标识相等比较，实际语义检查仍归冻结B worker/rules。prepared里非null的expected_candidate对candidate_id/format/该role InputSpec.expected_sha256有强制等式。声明A/B不一致→登记前InvalidExecutionSpec，不启动/不造record；声明一致A、H实际捕获B→登记和实际绑定后not_started固定记录（提交失败例外）。无预期prepare保持原prepared不变；captured-sha256@1允许无caller预期，但H仍须捕获实际sha并运行留存副本；expected-sha256@1强制非null expected。artifact来源还必须满足source_ref.sha256=expected_sha256。B按固定record重核，不把source原路径或自报id当证明。

H InputBinder在授权来源捕获实际字节，若与caller/Ref预期不符，可以把实际B留为**新ArtifactRef(B)**及失败事实，但绝不把B冒充原Ref(A)；不可把普通ArtifactReader的hash失败当“验证成功”。B读取新Ref仍按新hash验证，核查失败记录也不等于拿错整个顶层record。

### 2. 记录耗时和拒绝编码

记录级elapsed_seconds=本attempt claim成功到该payload**封存测量点**的以monotonic时钟测得的已观测时长，排除封存后编码/落盘/commit，不定义无法在自身字节内观测的“commit结束耗时”。step.elapsed_seconds=实际进程启动到确认结束；未启动null。前置耗时未观测时记录级也null，不能用0填未知。v2 golden将not_started record elapsed与wall-time usage改null/unknown/not_observed，所有依赖hash同步更新；这仍是文档向量，不是实测执行。

已登记且未取得需清理资源的准入/身份拒绝：phase=finished、process_outcome=not_started、started=false、cleanup=not_needed。若先已取得资源，release确认后cleanup=confirmed；未确认则phase=recovery_required/cleanup unknown或failed。不能为统一phase而抹租约。

### 3. 请求重入/崩溃结果表（先digest，再状态，绝不拿锁空闲当未启动）

| 已登记同key情况 | 唯一结果 |
|---|---|
| digest不同 | RequestConflict，原请求不变 |
| finished且commit完整 | 返原固定RecordRef，owner尚在释放锁亦不重跑 |
| recovery_required/side_effect_unknown | RecoveryRequired，latest_ref若有，仅核对/清理，绝不执行 |
| 非终态+owner锁有效 | AttemptInProgress，不等待/不做新绑定 |
| 非终态+锁空闲/owner未知，无commit或仅旧running修订 | RecoveryRequired；即使是registered行或OS已释放锁，也不能自动恢复/重跑 |
| 状态宣称finished而对应payload丢失/坏hash | RecordIntegrityError，不启动 |
| 无登记 | 原子claim；登记失败无本次启动 |

H01-4必须含外部副作用后、record提交前崩溃；重开进程看到锁空闲也只RecoveryRequired。对象写入、claim事务、记录事务、响应丢失各崩溃点分别验。SQLite本地事务不是外部副作用exactly once。

**D023-5 补充**：同一已保存 `AppsExecuteRequest` 的断连重放必须落在本表：已完成→原 RecordRef；未知→RecoveryRequired；不新分配 attempt、不延长期限/预算。

### 4. Reader命名空间

StorageMount.namespace为1–128位[A-Za-z0-9][A-Za-z0-9._-]*稳定本地命名空间；默认可生成UUID，但显式demo也合法，创建后不得悄改。root须是显式授权的非空本地绝对路径。StorageMount.prefix是不带末尾斜杠的规范相对路径，如archives/demo或stores/demo；匹配需location以prefix+"/"开头。在一次操作的配置里prefix两两既不相同也不互为祖先；配置重叠在读之前InvalidRequest；合法配置下Ref不匹配则UnsafeArtifactPath，不轮询读第二个根。directory reader将剩余相对段限制在授权root，拒链接/路径穿越；harness_sqlite reader只解析指定namespace固定attempt/version原BLOB。namespace需与mount前缀末段及store标识匹配。root是可信显式StorageConfig的本地路径，不从ArtifactRef/归档内容接受根配置，不联网。配置中的archive_namespace/harness_namespace必须各唯一匹配mount；archive写必须directory，execute的H写必须harness_sqlite，离线assess可用directory导出替换只读store mount，写能力由Apps/H各自构造，不把通用reader升级成writer。可离线导出用一个显式directory mount替换同prefix store reader，但不能同时叠两个读者；字节/hash/顶层身份检查一项不减。

### 5. PublicError.code有限枚举与映射（精确大小写）

| 情形 | code |
|---|---|
| 非H输入字段非法/重复结果键/无合法主claim选择 | InvalidRequest |
| H execute声明schema/路径/预期/role不合法，未登记 | InvalidExecutionSpec |
| 明确不支持的executor/operation声明（已登记缺执行能力则走not_started，不走本code） | UnsupportedOperation |
| 未知新信封schema主版本 | UnsupportedSchema |
| 冻结task/grader/assessor/identity rule版本不支持 | UnsupportedRuleVersion |
| 合法解析后顶层prepared/record/attempt/operation/scope/语义ID不匹配 | IdentityMismatch |
| 旧K CAS/revision不一致 | RevisionConflict（旧原生异常/编码不改；新适配可映射此code） |
| 同key不同digest | RequestConflict |
| 同key仍owner有效进行中 | AttemptInProgress |
| 无法证明可安全结束/旧非终态锁空闲 | RecoveryRequired |
| H登记/对象/commit存储失败 | ExecutionPersistenceError |
| Apps prepared/assessment字节归档失败 | ArchivePersistenceError |

### 2. 精确请求和结果

schemas新增AppsPrepareRequest(request=PrepareRequest)、AppsExecuteRequest(prepared_ref,proposal,attempt,output_root)、AppsAssessRequest(record_ref,primary_scope,primary_claim_id)，均schema_version=1、字段全required。StorageConfig由可信宿主显式注入，不进入协议/候选hash，取消信号是宿主句柄不是序列化DTO。Apps读取fixed prepared进行角色替换，不从路径找latest、不新造attempt/延长deadline/预算。

AppsResultV1字段全集以schema为准：schema_version/operation/outcome/reason_code/exit_code/primary_scope/primary_claim_id/attempt_id/admission/execution/prepared_ref/record_ref/assessment_ref/assessment/error，缺席显式null。execution为真正成功提交后的平铺ExecutionRecord，record_ref必须等于其中ref；execution非null时admission=execution.budget_admission、prepared_ref=execution.prepared_ref、attempt_id=execution.attempt_id。assessment非null时其record_ref/prepared_ref/attempt_id也须等于外层字段，assessment_ref非null须匹配其id/version/hash。操作失败且无execution/assessment时不靠输入声明假造结果字段；部分事实只放error.partial_record。assessment可在归档失败时保留内存B结果，但assessment_ref必须null；prepare归档失败不造PreparedRef；execute错误仍可并列已有latest_record_ref，不能冒充本次新Ref。reason_code只复制error.code或null，不私选task reasons。assess主key必须是固定协议/结果中唯一的精确claim key，不允许Apps对多个claim聚合。

CLI：inferrsi evaluate prepare/execute/assess；各*-ref参数采用`@<本地JSON文件>`，文件为完整对应Ref而非位置字符串/hash；request参数`--request @<JSON文件>`对应上述Apps*Request（execute额外ref参数如同时存在须精确等于request，否则InvalidRequest）。`--storage-config <本地JSON配置文件>`显式提供StorageConfig。assess request内primary_scope/primary_claim_id必须存在，命令行若提供--scope/--primary-claim必须相同；不得默选第一项。Ref文件按严格JSON解码/对应schema校验；规范payload/身份仍按D017逐字节，不把Ref参数文件本身当payload。兼容旧CLI不接受/解释这些新flags，直到后续Apps实现正式切片合入。

### 3. 退出/结果矩阵（0不是全局PASS）

| 操作/情况（按本表先后） | outcome/exit |
|---|---|
| 任意当前操作记录提交/归档失败 | persistence_error/6，缺本次有效Ref；保存B结果与保存错误并列 |
| PublicError RecoveryRequired / AttemptInProgress | recovery_required/5；in_progress/4；不启动新运行 |
| 其他PublicError | error/2，不伪造业务FAIL |
| execute已提交phase=recovery_required | recovery_required/5，保留新固定RecordRef但不同于重入异常 |
| execute已提交not_started | not_started/3；三预算/绑定失败事实留在execution；不是FAIL |
| execute已提交timed_out/cancelled/execution_error，或exited且exit_code非0 | execution_failed/7，不是B FAIL |
| execute其余完整受支持正常结束 | success/0，仍非B PASS |
| prepare归档成功 | success/0、有效PreparedRef |
| assess已归档且所选精确主claim PASS/FAIL/INCONCLUSIVE | success/0、fail/8、inconclusive/9；保留其他scope/claim完整结果且不覆盖 |

assess只按B结果与归档状态，不用历史执行非0覆盖独立claim；没有合法主key则InvalidRequest而不是Apps自选。exit2保留通用边界错误明细code。结果字段引用之间必须一致，不能有ref就当成功。后续统一事件按#333单独实现，不把本信封当旧事件schema。首批不新增CLI故新命名/选claim的实现不是今天P0/K01/H01额外前置。

**D023-4 主 claim 校验顺序（替代本节的“选claim”实现细节）**：读到合法固定 protocol 后先用 B 公开的只读 claim-key 能力或明确无业务投影核对请求键——键不在协议或缺合法主键→`InvalidRequest`/exit 2，不调用 assessor、不写 assessment；键在协议但 B 结果遗漏→`AssessorError` 类结果契约错误，不补判、不误报为用户参数错误；合法完整结果时归档失败优先（exit 6，`assessment_ref` 必须 null），成功后按所选 claim 返回 0/8/9。

**D023-5 CLI attempt 保存与断连重放**：`AppsExecuteRequest.attempt` 必填，`execute` 不再自行 `allocate_attempt`；`StorageConfig` 由可信宿主或显式 `--storage-config` 注入，不进入 `Apps*Request`。首期受支持路径为宿主先 `allocate_attempt`、执行前保存完整 `AppsExecuteRequest`、再把该文件交给 CLI。断连重放须重用原 attempt/原请求：已完成→原 `RecordRef`；未知→`RecoveryRequired`；不新分配、不延长期限/预算。P0a 不扩命令集，K01/H01 仍不实施 CLI。
